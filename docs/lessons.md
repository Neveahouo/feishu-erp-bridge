# 踩坑记录

按"遇到时的痛苦程度"排序。每条都附了判断方法和修法。

## 1. 飞书机器人读不到群消息

**现象**：私聊正常，群里 @ 机器人毫无反应。日志里群发现成功，但拉消息全是空。

**报错**：

```
230027 access denied for this bot operation
```

**原因**：飞书 OpenAPI 的 `im/v1/messages` 对 **bot 身份读群历史**有限制。机器人能看到自己所在的群列表，但读不了群里的聊天记录。

**修法**：群消息用 `user` 身份读（用户本人是群成员，有权限），私聊仍用 `bot`，发消息用 `bot`：

```python
identity = "user" if kind == "group" else "bot"
```

**判断口诀**：读群用 user，读私聊用 bot，发消息用 bot。

## 2. lark-cli 在 Windows 上吞参数

**现象**：命令行手敲完全正常，Python `subprocess` 调就报"缺少参数"。

**原因**：Windows 上 `lark-cli` 实际是 `.cmd` 批处理。用列表传参时，cmd 的参数解析层会吃掉某些参数（比如 `--sheet-id 84e3d3` 里的值）。

**修法**：用 `bash -lc` 包一层，并手动 quote：

```python
cmd = f"{LARK_CLI} " + " ".join(shlex.quote(str(a)) for a in args)
subprocess.run(["bash", "-lc", cmd], ...)
```

**附带问题**：Windows 控制台默认 GBK，`utf-8` 解码可能失败。稳妥做法是先 `utf-8` 解，异常再回退 `gbk`。

## 3. `rstrip(".0")` 会吃掉真实的尾零

**现象**：条码 `6900000000000` 写入后变成 `69`。

**原因**：`str.rstrip(".0")` 的语义是"删除结尾属于字符集 {'.', '0'} 的任意字符"，不是删除后缀 `".0"`。所以 `"6900000000000".rstrip(".0")` → `"69"`。

**修法**：

```python
def _drop_dot0(s):
    s = str(s).strip()
    return s[:-2] if s.endswith(".0") else s   # 只删最后两个字符
```

这类 bug 特别隐蔽：大部分条码不以 0 结尾，测试时看不出来。

## 4. 模板里的空白 Sheet 导致导入失败

**现象**：文件在 Excel 里打开完全正常，系统导入却报"文件无效"。

**原因**：模板自带 `Sheet2`、`Sheet3` 等空白页，本方解析器只读第一个 sheet，但**对方后端会校验整本文件**。

**修法**：fork 文档后统一清理：

```python
for name in list(wb.sheetnames):
    if name == keep:
        continue
    ws = wb[name]
    if ws.max_row <= 1 and ws.max_column <= 1:   # 只删空白页，有内容的别动
        del wb[name]
```

建议做成**双重保险**：既清理模板本身，也在每次 fork 后兜底清理一次。

## 5. 模板的"示例行"是活数据

**现象**：每次导入都多出一条不存在的商品。

**原因**：模板第 2 行是官方示例（`示例经营体` / `6900000000000` / 数量 100），系统导入时不会自动过滤。

**修法**：写入前按标记识别并删除：

```python
SAMPLE_ROW_MARKERS = {"B": "示例经营体", "D": "6900000000000"}
```

注意要按**多个字段**判断，只匹配一个容易误删真实数据。

## 6. 发文件必须用相对路径

**现象**：`lark-cli im +messages-send --file /abs/path.xlsx` 直接报错。

**修法**：把文件复制到工作目录下的子目录，切 `cwd` 后用 `./relative/path` 发送。

## 7. 电脑休眠后进程"变聋"

**现象**：进程还在（tasklist 能看到），日志每分钟都在写，但所有飞书调用都失败，错误信息还是空的。

**原因**：系统休眠/唤醒后，长期运行的进程可能丢失网络上下文或子进程环境，表现为静默失败。

**判断方法**：

- 手动执行同样的 `lark-cli` 命令 → 成功；
- 进程内的调用 → 全失败。
- 两者一对比，就知道是进程环境坏了，不是凭证过期。

**修法**：

1. 运行机器的电源计划设为**从不睡眠**；
2. 加**健康检查**：连续 N 轮全失败就自动重启进程（而不是无限空转）；
3. 用 Windows 服务或任务计划程序托管，崩溃自动拉起。

> 这个坑最值得写进告警：**"进程活着"不等于"功能正常"**。监控要看业务成功率，不是看进程是否存在。

## 8. 中文文件名与编码

**现象**：生成的 Excel 文件名在 Linux 上正常，在 Windows 上乱码。

**原因**：Windows 默认代码页是 GBK，Python 写文件时用了 UTF-8。

**修法**：

- Python 内部一律 UTF-8；
- 写给用户双击的 `.bat`，文件本身保存为 **GBK**，开头 `chcp 936 >nul`；
- 不要用"UTF-8 文件 + `chcp 65001`"的组合——在某些 Windows 版本上这会让中文行整体解析错乱。

## 9. 同名文件导致"累加变翻倍"

**现象**：同一商品连续加单两次，第二次数量是第一次的两倍。

**原因**：生成的文档名相同，旧文件被复用，引擎在已有行上又累加了一次。

**修法**：`fork_document()` 里同名文件先删除，保证每次都是干净副本。同时上层用 `message_id` 幂等挡住重复消息。

---

## 10. 推送时不要"全选"

**现象**：帮同事的单子一起提交了审批。

**原因**：草稿列表是**账号级**的，不是**本次操作级**的。直接 `query(status=0)` 拿到的可能是所有人的草稿。

**修法**：推送前按**本次涉及的条码/日期**过滤，只推自己刚导入的那几条：

```python
ids = [x["id"] for x in drafts if x["productBarCode"] in barcodes]
```

并且在 API 层强制 `confirm=True` 才能推送，防止调试脚本误触。
